# ADR-0011: v0.1 scope — small, but obeys every hard rule

- **Status:** proposed
- **Date:** 2026-10-02
- **Deciders:** Towheed (pending review)

## Context
The v0.1 roadmap broke the repo's own rules:

- The Docker provider shipped only five verbs (`plan, apply, status, logs, destroy`),
  violating rule 4 (no partial providers).
- No authentication, RBAC, or audit item — rule 10 says these exist from the first commit.
- `kiln rollback` was promised, but the rollback verb was deferred to v0.2.
- Builds were required on "dedicated builder nodes", impossible on the one VPS v0.1 targets.
- No ingress, so it was unclear how Kiln-deploys-Kiln is reachable.
- No measurement of whether the stack fits the 2GB box ADR-0001 promises.

ADRs 0007–0010 also change what v0.1 must contain.

## Decision
v0.1 is **one VPS, one tenant in practice (but tenant-scoped in schema and API), Docker
only, CLI only.** It contains:

1. **Contract:** `proto/` defines Tenant, Project, Environment, Service, Release,
   Deployment, and the agent protocol (ADR-0007). Every resource has `tenant_id`.
   Actors and approvers come from the authenticated principal, never from request fields.
2. **Data:** Postgres schema with `revisions`, `audit_events` in the same transaction,
   row-level security on `tenant_id`.
3. **Access:** API tokens (stored hashed). Three fixed roles per project — `viewer`,
   `deployer`, `owner` — checked on every RPC. Every mutation writes an audit event.
   SSO, SCIM, and custom roles stay in v1.0.
4. **Agent:** bootstrap-token registration, mTLS, outbound stream, sealed secret cache
   (ADR-0008), offline reconcile loop.
5. **Docker provider:** `Describe` + all seven verbs, conformance suite green. No partial
   provider, even in v0.1.
6. **Workflow:** Temporal deploy workflow: build → push → assign → wait healthy →
   finalize, with compensation "assign last healthy release". `kiln rollback` uses the
   same workflow (ADR-0010). Compensation tested before the forward path merges.
7. **Build:** BuildKit, Dockerfile only. **Single-node mode may build on the serving
   node**, with CPU/memory limits on the build. Dedicated builders apply once there is
   more than one node.
8. **Secrets:** OpenBao as the one supported backend, shipped in the install bundle.
   Envelope encryption and per-environment keys stay v0.2.
9. **Networking:** no Kiln-managed proxy. Services publish host ports. TLS, DNS, and Caddy
   stay v0.2.
10. **Footprint gate:** measured idle and mid-deploy memory of the full stack (Postgres,
    Temporal, OpenBao, Kiln, BuildKit) on a 2GB VPS, published in `docs/`. If it does
    not leave ≥1GB for workloads, ADR-0002 is reopened before v0.2.
11. **Housekeeping the rules depend on:** `.claude/skills/new-workflow/` (referenced by
    ADR-0002) and `deploy/dev/compose.yaml` (referenced by the Makefile).

**Exit criterion unchanged:** Kiln deploys Kiln, and rolls itself back.

## Alternatives considered
- **Keep the original six-week list.** Faster to a demo. Lost because it ships a partial
  provider and a system with no auth or audit; both are rule violations, and rule 10
  exists because retrofitting them is the known failure mode.
- **Defer access control but keep tenant_id columns.** Half the work. Lost because
  "who did this" must be answerable from the first deployment that touches Kiln itself;
  an audit log with no authenticated actor is not an audit log.
- **Ship Caddy + automatic TLS in v0.1.** Nicer demo. Lost on scope: Kiln-deploys-Kiln
  works over a host port, and ingress is a whole subsystem.
- **Defer Exec and Scale to v0.2 by marking them `ErrUnsupported`.** Technically allowed
  by the spec's rule 1. Lost because Docker can obviously do both; declaring them
  unsupported would be a partial provider in disguise.

## Consequences
- v0.1 is larger than "weeks 1–6". Realistic estimate: **weeks 1–10**. The roadmap is
  updated to say so rather than pretend.
- v0.2 loses "remaining provider verbs" and "RBAC surfaced in API"; it keeps UI exposure
  of audit/RBAC.
- The footprint measurement can invalidate ADR-0002. That is the point of the gate.
- Single-tenant use with multi-tenant schema means some code paths (tenant creation,
  cross-tenant admin) exist but are lightly exercised; tests must cover them anyway.

## Revisit when
Week 6 passes with fewer than half the items above done — then cut scope explicitly by
superseding this ADR, never by silently dropping a rule.
