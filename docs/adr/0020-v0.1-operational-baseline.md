# ADR-0020: v0.1 operational baseline — what a single VPS needs to survive month one

- **Status:** proposed
- **Date:** 2026-10-21
- **Deciders:** Towheed

## Context
ADR-0011 fixed the v0.1 scope against the hard rules. It does not cover the ways a
single-VPS platform fails in practice. None of these is a feature; each one breaks a
promise in `00-vision.md` if it is missing:

1. **The disk fills up.** Old images, BuildKit cache, and container logs grow without
   bound. On one VPS this is the most common cause of a dead platform. Rollback
   (ADR-0010) also depends on old images still being present, so cleanup and rollback
   pull in opposite directions and need one rule.
2. **"build → push" has no registry.** The ADR-0011 workflow pushes an image, but v0.1
   ships no registry, and running one costs memory the 2GB budget may not have.
3. **Host-port deploys are not zero-downtime.** With no proxy in v0.1 (ADR-0011 item 9),
   the new container cannot bind the port until the old one stops.
4. **OpenBao seals on reboot.** After a VPS reboot, deploys cannot resolve secrets until
   someone unseals it. Running workloads survive (sealed cache, ADR-0008); deploys do not.
5. **Nothing backs up Bohux itself.** Losing the control-plane disk loses the revision
   history, the audit log (rule 10), the secret values, and the node CA.
6. **Agents and control plane will run different versions** from the first upgrade, and
   self-upgrade is v1.0.
7. **The Docker daemon restarts** (package upgrades, OOM). Without `live-restore`, every
   container stops with it.
8. **The footprint gate runs too late.** ADR-0011 measures memory at the end of v0.1. Its
   outcome can reopen ADR-0002 (Temporal), which everything else builds on.

## Decision
v0.1 adds the following to ADR-0011. ADR-0011 stays in force; this extends it.

1. **Footprint first.** Before feature work, run the stack (Postgres, Temporal, OpenBao,
   BuildKit, a stub Bohux binary) on a 2GB VPS, measure idle and during a build, and
   publish the result in `docs/`. The ADR-0011 gate (≥1GB left for workloads) applies
   to this week-1 number and is re-measured at the end of v0.1.
2. **No registry in single-node mode.** BuildKit exports straight into the node's local
   image store. A Release records the image ID (content digest); the workflow's "push"
   step is a no-op in single-node mode. A registry becomes required when the second node
   joins, by its own ADR.
3. **Retention tied to rollback.** The agent keeps images for the currently assigned
   Release plus the last **5** Releases per App, and deletes older ones. A Release whose
   image is gone is shown as "not rollback-able" in the API and CLI, never as a silent
   failure at rollback time. BuildKit cache is capped (default 10GB, configurable).
   Container logs use Docker's `json-file` driver with size rotation (default 3 × 10MB).
4. **Disk pressure fails closed.** Below a free-disk threshold (default 10%), the agent
   refuses new builds and reports the node as degraded through the stream. Running
   workloads are untouched (rule 1).
5. **v0.1 deploys may have downtime, and say so.** Stop-old/start-new on the host port is
   the v0.1 behaviour. The CLI prints a warning, and the downtime is measured in the
   self-deploy test. Zero-downtime arrives with ingress in v0.2 (ADR-0019).
6. **OpenBao auto-unseals.** The install bundle configures auto-unseal with a node-local
   key (TPM-bound where available, else a 0600 file owned by the Bohux user, same
   posture as ADR-0008). The trade-off goes in the threat model.
7. **Bohux backs itself up.** `bohux admin backup` writes one archive containing a
   Postgres dump, an OpenBao snapshot, and the node CA. A scheduled nightly backup goes to a
   user-configured path or S3-compatible bucket, and `bohux admin restore` restores it
   onto a fresh host. A CI test does backup → wipe → restore → `bohux rollback` against
   the restored state. Archives contain secret values: encrypted at rest with a key the
   operator holds, never logged (rule 3).
8. **Version skew is in the protocol.** The agent sends its version on stream open; the
   control plane accepts agents of the same and previous minor version and rejects older
   ones with an explicit error. Agents keep reconciling their last known state while
   rejected (rule 1).
9. **Docker `live-restore` is required.** The agent checks it at registration and refuses
   to register without it, with a message naming the setting.

## Alternatives considered
- **Leave these to v0.2+.** Smaller v0.1. Lost because the v0.1 exit criterion is "Bohux
  deploys Bohux and rolls itself back", and items 2, 3, 5 and 7 are on that exact path.
  A self-deploy that fills the disk or cannot be restored proves nothing.
- **Ship a local registry (`registry:2`) in v0.1.** Matches the multi-node shape early.
  Lost on the memory budget and on adding a component that one node does not need.
  Image IDs carry over: a registry push later adds a manifest digest without
  changing the Release.
- **Time-based image retention (e.g. 30 days).** Lost because rollback depth is what users
  care about; a quiet app would lose its rollback targets on a timer.
- **Manual unseal with a documented runbook.** Best key hygiene. Lost because an unattended
  reboot at 3am would block deploys, including the rollback that fixes an incident.
- **Backups via the user's own tooling.** Fewer features. Lost because the vision promises
  "backups are proven by restore drills", and that has to hold for Bohux's own state first.

## Consequences
- v0.1 grows by roughly two weeks. The roadmap reflects this rather than hiding it.
- Retention means rollback depth is finite (5 Releases by default). This is documented
  and visible per Release.
- Auto-unseal with a local key means root on the VPS can read secrets. That was already
  true through the sealed cache (ADR-0008); now it is stated in one place.
- Backup archives become the most sensitive file Bohux produces. Their encryption key
  handling needs a runbook (`write-runbook`).
- The agent protocol (ADR-0007) gains a version field and a rejection message before
  `proto/` freezes.
- Multi-node installs need a registry ADR before the second node can join.

## Revisit when
The week-1 footprint measurement leaves less than 1GB for workloads (reopen ADR-0002), or
users report rollback depth of 5 as too shallow in at least three issues.
